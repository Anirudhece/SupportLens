# Research M0 — Vector Database Selection

## Status

- **Decision:** ChromaDB is the primary vector database for SupportLens.
- **Decision date:** 2026-08-27
- **Evidence type:** Architecture research and discussion; no implementation benchmark has been performed.
- **Related documents:** `docs/PROJECT_CONTEXT.md` and `docs/PRD.md`

## Question

Which vector database best supports SupportLens's current product, learning, portfolio, and interview goals?

The decision must keep the core RAG pipeline understandable, support meaningful embedding experiments, and avoid adding technology whose main learning value is outside the project's Applied AI focus.

## Decision criteria

The options were compared using these criteria:

- Relevance to Applied AI and RAG engineering.
- Ability to inspect and explain vector retrieval behaviour.
- Ability to use automatic, hosted, or locally generated embeddings.
- Ease of comparing multiple embedding models.
- Local development cost and operational complexity.
- Additional interview surface created by the choice.
- Suitability for a staged learning project rather than only a quick demo.
- Ability to keep embedding generation and vector storage modular.

## Options considered

### PostgreSQL with pgvector

pgvector adds vector similarity search to PostgreSQL and supports exact search, approximate HNSW and IVFFlat indexes, metadata filtering through SQL, and hybrid retrieval with PostgreSQL full-text search.

Its original advantage for SupportLens was learning PostgreSQL and vector search together. That advantage became a mismatch after clarifying the project goal: PostgreSQL is not currently a desired learning objective, and listing it as a central project technology would create a reasonable expectation that the implementation can defend SQL, relational modelling, query planning, and PostgreSQL indexing decisions.

**Outcome:** Not selected. The technical capability is strong, but the additional SQL learning and interview surface are outside the narrowed project focus.

### Pinecone

Pinecone is a managed vector database. It supports indexes with integrated hosted embedding models and indexes that accept vectors generated by an external model. Integrated embedding can accept source text during ingestion and queries, allowing Pinecone to perform both embedding generation and vector retrieval.

Its principal advantages are low operational effort and a managed-production story. The trade-offs are reliance on an external service, account and network requirements, quota or pricing dependence, and greater abstraction of the embedding and storage infrastructure. An integrated embedding index is also tied to its configured model; changing models requires a different compatible index and re-ingestion.

**Outcome:** Not selected as the primary database. Pinecone remains a possible later managed-service comparison after the local retrieval pipeline is understood and evaluated. That comparison is optional and not yet a committed milestone.

### ChromaDB

ChromaDB is an open-source, AI-focused vector database that supports local development and hosted deployment. A collection can generate embeddings through an embedding function or accept precomputed embeddings from the application.

If no custom function is selected, Chroma's default embedding function uses the open-weight `all-MiniLM-L6-v2` model locally. Chroma therefore does not provide a proprietary default embedding model; it provides an integration that downloads and runs an existing open model.

The application can later generate embeddings explicitly with another local or hosted model and pass those vectors to ChromaDB. This supports an incremental learning path without requiring the storage system to change.

**Outcome:** Selected. It keeps the project focused on vector retrieval and embedding experimentation, avoids an unrelated SQL learning requirement, and permits both automatic-baseline and explicit custom-embedding implementations.

### MongoDB Vector Search and other alternatives

MongoDB Vector Search, Qdrant, and Weaviate were considered earlier. MongoDB would reuse an existing résumé skill but add less new vector-database experience. Qdrant and Weaviate are credible vector databases, but the active discussion was deliberately narrowed to Pinecone and ChromaDB to avoid expanding the decision indefinitely.

**Outcome:** Not selected for the initial implementation and not scheduled as migration targets.

## Final decision

SupportLens will use **ChromaDB as its primary vector database and retrieval system**.

The intended learning progression is:

1. Establish a working ChromaDB retrieval baseline.
2. Keep document loading, chunking, embedding, storage, and retrieval as explicit pipeline stages.
3. Introduce an application-owned embedding-provider boundary.
4. Compare suitable local or hosted embedding models using the same corpus and evaluation questions.
5. Consider a managed vector-database comparison only after the ChromaDB baseline is understood and measured.

## What this decision does not finalize

This decision does not select:

- The initial embedding model.
- Whether the first baseline uses Chroma's automatic embedding function or embeddings generated explicitly by Express.
- Nomic, Qwen, MiniLM, Pinecone Inference, or any other permanent embedding provider.
- Local ChromaDB versus Chroma Cloud for deployment.
- Collection persistence, backup, authentication, or production-hosting strategy.
- A future Pinecone implementation or migration milestone.

Those decisions require separate approved plans and, where meaningful, measured experiments.

## Embedding-model compatibility constraint

Document and query vectors must be generated by the same compatible model and configuration. Vectors from different embedding models cannot be mixed merely because they have the same number of dimensions.

Changing the embedding model requires re-embedding the stored corpus. During comparisons, separate collections may be used for each model so that every candidate is evaluated against the same chunks, metadata, and queries without contaminating vector spaces.

Example experimental collection names could be:

```text
supportlens_minilm
supportlens_nomic
supportlens_qwen
```

These names illustrate a possible experiment design; they are not approved implementation names.

## Revisit conditions

The vector-database decision should be revisited only if evidence shows that ChromaDB cannot meet a documented requirement, such as:

- Required metadata or hybrid-retrieval behaviour cannot be implemented reliably.
- The selected deployment model cannot meet security, persistence, availability, or scaling requirements.
- Measured ingestion or retrieval performance fails a milestone gate.
- A managed-service comparison demonstrates a meaningful quality or operational advantage that justifies migration.

Popularity alone or an unsupported benchmark claim is not sufficient reason to migrate.
